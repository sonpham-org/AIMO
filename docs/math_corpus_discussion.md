# GPT-OSS-120B Math Reasoning Traces with Logprob Signals — Math Corpus Submission

## Overview

We release **1,184 reasoning traces** (74 problems x 16 samples) generated by **gpt-oss-120b** on an NVIDIA H100 GPU. Each trace includes full multi-turn reasoning with tool-integrated reasoning (TIR), **per-token logprobs**, **per-token entropy**, and **24 per-sample quality signals** — making this one of the most richly annotated math reasoning trace datasets available.

Unlike most trace datasets that only store the final text, our traces preserve the **probability landscape** of the model's reasoning process, enabling research into confidence-based answer selection, process reward modeling, and self-consistency analysis.

## What Makes This Dataset Unique

### 1. Per-Token Entropy and Logprobs

Every sample stores:
- **`chosen_logprobs`**: Per-token log-probability of the model's chosen token — enables PRIME-style reward estimation, DPO training signal computation, and self-certainty scoring
- **`per_token_entropy`**: Full entropy trajectory across the reasoning chain — enables DeepConf-style confidence analysis and process reward model (PRM) step-level reward estimation
- **`cumulative_logprob`** and **`length_normalized_logprob`**: Sequence-level scores for ranking solutions

To our knowledge, no existing public math reasoning dataset includes per-token probability distributions. This enables novel research into:
- **Confidence-weighted voting**: Weight solutions by model certainty, not just majority vote
- **Process reward modeling**: Use entropy trajectories as step-level reward signals without training a separate PRM
- **Uncertainty detection**: Identify where in the reasoning chain the model is least confident

### 2. Tool-Integrated Reasoning (TIR) Traces

64% of samples use Python code execution via Jupyter kernels:
- **Code success rate: 97.3%** across 3,834 code calls
- Full turn structure preserved: text reasoning → code → code output → text reasoning
- Enables training TIR-capable models

### 3. Rich Per-Sample Quality Signals (24 fields)

Each of the 1,184 samples includes:

| Signal | Description | Use Case |
|--------|-------------|----------|
| `entropy` | Mean entropy across all tokens | Confidence-weighted voting |
| `entropy_std` | Entropy standard deviation | Reasoning stability |
| `entropy_min/max/p10` | Entropy distribution stats | Outlier detection |
| `per_token_entropy` | Full entropy trajectory | PRM step rewards |
| `chosen_logprobs` | Per-token logprob list | DPO, PRIME, Self-Certainty |
| `cumulative_logprob` | Sum of all token logprobs | Sequence scoring |
| `length_normalized_logprob` | Logprob / token count | Length-fair scoring |
| `code_calls/errors/success_rate` | TIR quality metrics | Code reliability |
| `all_turn_answers` | Answer at each turn | Answer stability |
| `answer_changed_count` | How often answer changed | Reasoning consistency |
| `answer_format_valid` | Correct \boxed{} format | Format reliability |
| `ngram_rep_4` | 4-gram repetition ratio | Degeneration detection |
| `finish_reason` | stop vs length | Truncation detection |
| `is_correct` | Ground truth correctness | SFT/DPO labels |

### 4. Problem-Level Aggregates

Each problem JSON also includes:
- `pass_rate`: Fraction of 16 samples that got the correct answer
- `n_correct`: Count of correct samples
- `answer_distribution`: Frequency of each unique answer — enabling majority vote analysis

## Key Findings from This Data

### Correctness Rates

| Source | Accuracy |
|--------|----------|
| limo | 89.4% (186/208) |
| bigmath | 56.8% (227/400) |
| aimo3_hard | 27.9% (156/560) |
| Overall | 48.2% (571/1,184) |

### Signal Discrimination (Correct vs. Incorrect)

| Signal | Correct | Incorrect | Delta |
|--------|---------|-----------|-------|
| Mean entropy | 0.751 | 0.909 | -17% |
| Normalized logprob | -0.333 | -0.369 | +10% |
| Completion tokens | 3,783 | 6,166 | -39% |
| N turns | 3.0 | 5.2 | -42% |
| Code calls | 2.0 | 4.4 | -54% |
| N-gram repetition | 0.070 | 0.112 | -38% |
| Time (seconds) | 19.8 | 32.3 | -39% |

**Key insight**: Correct solutions are consistently shorter, more confident (lower entropy), and use fewer code calls. This validates entropy as a lightweight signal for answer selection.

### Problem Difficulty Distribution

| Difficulty | Count | Description |
|------------|-------|-------------|
| 16/16 correct | 23 | Trivial (model always gets it) |
| 9-15/16 | 7 | Easy (mostly correct) |
| 4-8/16 | 15 | Medium (mixed results) |
| 1-3/16 | 13 | Hard (rarely correct) |
| 0/16 | 16 | Impossible (model never gets it) |

78% of problems (58/74) have at least one correct solution among 16 samples — the oracle upper bound. Majority vote achieves 56.8% (42/74), leaving a **21-point gap** that better selection strategies could close.

## How to Use This Data

### For Training (SFT)
Filter for `is_correct == true` samples. Optionally rank by `length_normalized_logprob` to select highest-quality correct solutions.

### For DPO/Preference Learning
Pair correct and incorrect solutions within each problem. Use `entropy` or `length_normalized_logprob` as a quality signal to rank among correct solutions.

### For Answer Selection Research
Use the 16 samples per problem to benchmark selection strategies:
- Majority vote (baseline: 56.8%)
- Entropy-weighted voting
- Logprob-weighted voting
- Process reward model scoring using `per_token_entropy`
- Oracle upper bound: 78.4%

### For Process Reward Modeling
The `per_token_entropy` field provides step-level uncertainty signals without requiring a trained PRM. Explore whether entropy spikes correlate with reasoning errors.
