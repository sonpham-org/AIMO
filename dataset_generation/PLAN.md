### 3.1 Track A: TIR Cold-Start SFT

**Objective**: Teach gpt-oss-120b better tool-use patterns, reasoning quality, and token efficiency.

**Source Data** (priority order):
1. **AIMO3 High-Difficulty** (7,293 problems, ~70K traces, with pass_rate metadata) -- generated by gpt-oss-120b itself
2. **AIMO3 TIR** (141K traces from gpt-oss-120b) -- large pool for selection
3. **LIMO** (817 curated CoT) -- proven quality exemplars
4. **s1K** (1,000 curated) -- proven quality exemplars

#### 8-Stage Curation Pipeline

```
Stage 0: Load & normalize all datasets
    → ~150K raw samples

Stage 1: Hard filters
    - Length: 500 - 100,000 chars
    - Tool calls: 1-20 (for TIR sources)
    - No boxed answer marker → reject
    - Repetitive patterns (80+ chars repeated) → reject
    → ~105K (70% retention)

Stage 2: Outcome verification (NEW - from researcher-3)
    - Extract \boxed{} answer via math_verify
    - Compare to ground truth via SymPy equivalence
    - For AIMO3 Hard: answer already verified in metadata
    - For AIMO3 TIR: need to extract and verify
    → ~50-70K (50% retention)

Stage 3: Decontamination
    - 9-gram overlap check vs: AIME 2023-2025, MATH500, GPQA Diamond, AIMO3 competition problems, HMMT 2025
    - 8-gram deduplication within training set
    - Embedding similarity check (cosine > 0.90 = remove) as supplement
    → ~48-65K (95% retention)

Stage 4: Difficulty calibration
    - Use pass_rate from AIMO3-Hard metadata where available
    - For AIMO3-TIR: estimate from answer distribution across solutions for same problem
    - Keep: pass_rate 0.03-0.30 for SFT
    → ~15-25K (30% retention)

Stage 5: Process verification (NEW - from researcher-3)
    - TIR integrity: all code blocks execute without errors, 100% tool success rate
    - Cross-model agreement: keep only solutions whose answer matches a Qwen3-8B reference
    - PRM scoring: ThinkPRM-14B or Qwen2.5-Math-PRM-7B step-level scores
    - Reject solutions where min_step_score < 0.5 (even if final answer is correct)
    → ~8-15K (50% retention)

Stage 6: Quality scoring
    Combined score (4 dimensions, 0-1 scale):
    - Difficulty (25%): pass_rate 0.03-0.15 = 1.0, 0.15-0.30 = 0.7, >0.50 = 0.1
    - Solution quality (35%): length, verification keywords, exploration, logical connectives
    - Interaction density (20%): tool calls >= 9 = best (ASTER finding)
    - Structural quality (20%): step numbering, boxed answer, sympy usage, no repetition
    → Rank all remaining samples

Stage 7: Difficulty-aware trace selection (NEW - from researcher-2)
    - Easy problems (pass_rate > 0.5): pick SHORTEST correct solution
    - Medium problems (0.15 < pass_rate <= 0.5): pick MEDIAN-length correct solution
    - Hard problems (pass_rate <= 0.15): pick HIGHEST-QUALITY solution (allow longer)
    - This teaches the model to think proportionally: easy = concise, hard = thorough
    → ~1 solution per problem

Stage 8: Diversity selection
    - Classify problems by topic (number_theory, algebra, combinatorics, geometry, probability)
    - Ensure minimum coverage per topic: >=150 for NT/algebra, >=100 for combo/geometry, >=75 for probability
    - Iterative balanced sampling weighted by difficulty * quality
    - Target: 3K-4K final examples
    → 3K-4K final dataset
```

#### Key Selection Criteria (from ASTER)
- >= 9 tool-interaction turns (4K dense trajectories beat 45K mixed)
- 100% tool execution success (no code errors in any code block)
- Multi-turn tool coordination (not single verify-at-end "interaction collapse")
- Correct final answer verified against ground truth AND cross-model
- Deliberative reasoning: think deeply before each tool call (DemyAgent insight)

### 3.2 Track B: GenSelect Training

**Objective**: Teach gpt-oss-120b to evaluate and select the best answer from N candidates. This directly addresses our core bottleneck: 16 attempts scoring WORSE than 8 because selection degrades.

**Why GenSelect is Critical**:
- NVIDIA's GenSelect: AIME24 89.2 -> 93.3 (+4.1), HMMT 73.8 -> 96.7 (+22.9)
- Our entropy heuristic works for 8 attempts but FAILS for 16+
- GenSelect is essentially a learned verifier integrated into the generator -- no separate model needed, no VRAM overhead

**Source Data**: nvidia/OpenMathReasoning GenSelect subset (566K samples, CC-BY-4.0)

**Curation**:
1. Download GenSelect subset from OpenMathReasoning
2. Filter to olympiad-level difficulty (pass_rate_72b_tir < 0.5)
3. Select problems with 4+ candidate solutions of varying quality
4. Keep 2K-5K highest quality examples
5. Format: multiple candidate solutions + selection reasoning + chosen answer

**Integration at Inference**:
- Generate N solutions per problem (N=16-32)
- Feed all N to the same model with GenSelect prompt
- Model outputs selection reasoning + chosen answer
- Replaces our entropy-weighted consensus entirely

### 3.3 Track C: RL Problem Set

**Objective**: Provide problems for GRPO reinforcement learning to improve reasoning.

**Source Data**: SynthLabsAI/Big-Math-RL-Verified (250K verified problems)

**Curation**:
- Filter to competition-level difficulty (olympiad / AIME-level)
- Require verifiable integer answers (for reliable reward signal)
- Goldilocks zone: pass_rate 0.10-0.70 (maximizes gradient signal)
- Target: 5K-10K problems

**Training**: Via Tinker API ($50-200, with $150 free credits for new users)
- Algorithm: GRPO with binary rewards (correct=1, wrong=0)
- Group size: 4-8 samples per problem
- Training steps: 100-200
- Length-aware reward (NEW - from researcher-2):
  ```python
  reward = correctness + 0.1 * cosine_length_bonus(length, target_length)
  # Only reward shorter outputs when the answer is correct
  ```

## 4. Token Efficiency Strategy (from researcher-2)

### 4.1 Three-Stage Training for Shorter Outputs

```
Stage 1: SFT on difficulty-calibrated traces (Track A, 2K-4K examples)
    - Easy problems: shortest correct trace
    - Hard problems: highest-quality trace
    - Include TIR traces with >=3 tool calls
    - Expected: baseline token efficiency from curation alone

Stage 2: DPO on length-preference pairs (2K-5K pairs)
    - Chosen: shorter correct solution (min_length=500 chars)
    - Rejected: longer correct solution (ratio_threshold=0.7)
    - Source: AIMO3 Hard dataset (8 solutions per problem with quality metadata)
    - This stage specifically reduces output verbosity
    - Expected: additional 10-20% token reduction

Stage 3: GRPO with length-aware reward (Track C)
    - Reward = correctness + 0.1 * cosine_length_bonus
    - Only penalize length for correct solutions
    - Dynamic difficulty targeting
    - Expected: additional 10-20% token reduction
```

### 4.2 DPO Pair Construction

```python
def construct_length_dpo_pairs(solutions_per_problem, ratio_threshold=0.7, min_length=500):
    """Build DPO pairs: chosen = shorter correct, rejected = longer correct."""
    pairs = []
    for problem_id, solutions in solutions_per_problem.items():
        correct = sorted(
            [s for s in solutions if s['is_correct']],
            key=lambda s: len(s['text'])
        )
        for i, short in enumerate(correct):
            for long in correct[i+1:]:
                if len(short['text']) >= min_length and \
                   len(short['text']) < ratio_threshold * len(long['text']):
                    pairs.append({
                        'prompt': solutions[0]['question'],
                        'chosen': short['text'],
                        'rejected': long['text']
                    })
    return pairs
```

### 4.4 Format Guidelines for Training Data

Training traces should follow concise format:
1. No preamble ("Let me think about this...")
2. Direct problem analysis (key observations first)
3. Code-first verification (Python/SymPy over manual algebra)
4. No redundant recapping (each step adds new information)
5. Concise error handling (brief fix, no elaboration)
6. Direct answer extraction (state answer immediately after computation confirms)

## 5. Verification Pipeline (from researcher-3)

### 5-Stage Verification (with resource assignments)

```
Stage 1: Outcome Verification (filter ~30-50%)
    Tool: math_verify + SymPy
    Platform: Local (CPU)
    Cost: $0 (milliseconds per solution)
    Action: Extract \boxed{} answer, compare to gold

Stage 2: TIR Integrity Check (filter ~10-20% of correct solutions)
    Tool: Structural analysis (Python)
    Platform: Local (CPU)
    Cost: $0
    Action: Verify code execution success, tool call count, no loops

Stage 3: Cross-Model Agreement (filter ~20-40% more)
    Tool: Gemini 2.0 Flash API
    Platform: Google API ($45 of $93 budget)
    Cost: ~$45 for 50K solutions (~250M input + 50M output tokens)
    Action: Generate independent answers via Gemini, keep gpt-oss-120b
            solutions only where Gemini agrees with ground truth.
            This catches "lucky correct" solutions with flawed reasoning.

Stage 4: Process Verification with PRM (score remaining)
    Tool: Qwen2.5-Math-PRM-7B (4-bit quantized, ~4GB VRAM)
    Platform: Kaggle H100 (alongside gpt-oss-120b)
    Cost: $0
    Action: Score each step, reject min_step_score < 0.5

Stage 5: Quality Ranking (select best per problem)
    Tool: Rule-based scorer + Gemini 2.0 Flash quality check
    Platform: Local + Google API ($9 for 10K finalists)
    Cost: ~$9
    Combined score = 0.30 * prm_avg + 0.25 * difficulty + 0.20 * quality_keywords
                   + 0.15 * interaction_density + 0.10 * cross_model_confidence
```

### Why Gemini 2.0 Flash for Cross-Model Verification

Cross-model verification (AceMath method) is the strongest filter for catching "right answer, wrong reasoning." Using Gemini as the second model is ideal because:
1. **Architecturally different** from gpt-oss-120b (reduces correlated errors)
2. **Very cheap** at $0.10/$0.40 per 1M tokens -- we can verify 50K solutions for ~$45
3. **Strong math capability** -- Gemini Flash models score well on math benchmarks
4. **No VRAM overhead** -- runs via API, doesn't compete with our H100 workload

### Available PRMs (Zero Cost)

| Model | Size | Type | Best For |
|-------|------|------|----------|
| **ThinkPRM-14B** | 14B | Generative (recommended) | Step verification, interpretable |
| **ThinkPRM-1.5B** | 1.5B | Generative (lightweight) | Quick screening |
| **Qwen2.5-Math-PRM-7B** | 7B | Discriminative | General math |
| **ReasonFlux-PRM-7B** | 7B | Trajectory-aware | Long CoT / TIR |

### PRM Mismatch Warning
No PRM exists for gpt-oss-120b specifically. Mitigations:
- Use generative PRMs (ThinkPRM) which generalize better than discriminative PRMs
- Use PRM scores as soft weights, not hard filters
- Combine with cross-model agreement for robustness

### 6.2 DPO Stage (for token efficiency)

After SFT, apply DPO on 2K-5K (short_correct, long_correct) pairs:
- Use OpenR1-Math-220k or AIMO3 Hard dataset for pair construction
- Ratio threshold: 0.7 (chosen must be <70% of rejected length)
- Enforce min_length=500 to avoid degenerate outputs
- 2-4 epochs (following Imagination team recipe)

### 6.3 Importance-Weighted SFT (iw-SFT)

Apply during SFT for +10% AIME improvement at zero extra data cost:
- Maintain frozen reference model
- Compute per-token log-probability differences
- Smooth and clip weights: `weight = 0.1 * clip(exp(rho), 0.2, 1.8)`
- Multiply loss by weight
- Reference: arxiv 2507.12856

### 6.4 GRPO RL (Tinker API, Track C)

- Algorithm: GRPO with binary rewards + cosine length bonus
- Group size: 4-8 samples per problem
- Training steps: 100-200
- LoRA rank: 64 (divided by active experts for MoE)
- Learning rate: 1e-4 to 5e-4
- Budget: $50-200 ($150 free Tinker credits)

| Risk | Impact | Mitigation |
|------|--------|------------|
| QLoRA on MoE degrades base quality | High | Test on small subset first; compare to baseline before full training |
| GenSelect format mismatch with Harmony protocol | Medium | Adapt format during curation; test with inference pipeline before training |
| LoRA merge + MXFP4 quantization quality loss | Medium | Test quantized model before submission |
| PRM mismatch (Qwen-trained PRM on gpt-oss outputs) | Medium | Use generative PRMs (ThinkPRM), soft weights not hard filters |
| Contamination with AIMO3 test problems | High | Strict 9-gram + Gemini semantic decontamination |
| Kaggle H100 session limits training time | Low | 4K SFT takes ~2-4h, well within 9h; split across sessions if needed |
| DPO causes quality degradation | Medium | Use min_length=500, verify accuracy after DPO stage |
| More attempts still hurt selection | High | GenSelect is the primary fix; fall back to 8 attempts if selection still degrades |
| Google API credits exhausted mid-pipeline | Low | Most critical use (cross-model verification) runs first; budget has $13 buffer |
| Gemini math errors in cross-model verification | Medium | Gemini is the FILTER, not the source of truth; false negatives just reduce dataset size, don't add bad data |

## 12. Anti-Patterns (What NOT to Do)

Based on all research and our own experience:

1. **Do NOT use all correct traces** -- quality >> quantity. Doubling mixed-quality data hurts (-5% per NVIDIA Front-Loading).
2. **Do NOT bias toward easy problems** -- DART showed standard rejection tuning is 90% easy problems.
3. **Do NOT keep "lucky correct" solutions** -- use cross-model verification + PRM to catch wrong reasoning.
4. **Do NOT ignore topic balance** -- geometry and probability are underrepresented in most datasets.
5. **Do NOT train on brute-force solutions** -- prefer algebraic/analytical approaches with code verification.
6. **Do NOT skip decontamination** -- must exclude AIME 2023-2025 and AIMO3 evaluation problems.
7. **Do NOT use excessively long solutions** -- >80K chars usually means stuck/looping.
8. **Do NOT add complexity to the selection heuristic** -- our experience: simple > complex (40/50 > 32/50). GenSelect replaces the heuristic entirely.
9. **Do NOT use latent reasoning approaches (Coconut/CODI)** -- incompatible with vLLM, too experimental.
10. **Do NOT aggressively compress hard problems** -- they need full reasoning depth. Only compress easy/medium.
